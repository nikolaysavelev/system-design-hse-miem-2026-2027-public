# Акт 1. Проблема: pay медленный, а инструменты занятия 3 молчат

Ветка `demo/l4-problem`, прогон 26.09.2026 с чистой БД (`make down && make up`), затем `make checkout-storm`:
checkout 150 VU × 90 с на мероприятии 2 и параллельно фоновый шторм 400 итераций/с на мероприятии 1.
Стенд: PSP 300 мс (in-process), почтовый шлюз `mailgw` 900 мс ± 30 %, 5 % ответов 502, клиент с таймаутом 2 с и одним повтором.

## Что говорим

Три инструмента занятия 3 отвечают одинаково: "не я". База работает 19 секунд из 100 и отвечает за доли миллисекунды,
CPU приложения меньше половины ядра, в профиле сетевые системные вызовы и планировщик. При этом pay в среднем
идет 1.25 с, а хвост 2.3 с. Время уходит на ожидание, а ожидание не видно ни в CPU, ни в SQL.

Вопрос студентам: из чего складываются 1.25 с? RED-метрики показывают только итог по маршруту; разбивки по этапам нет
(метрику `booking_pay_stage_seconds` намеренно не добавляли). Ответ даст трейс (акт 2).

## Расхождения со спекой (честно)

| Спека ожидала | Факт | Почему |
|---|---|---|
| ошибки 2-5 % | 0 % | ошибка `Send` только логируется, а таймаут хендлера 3 с не пробивается: p99 2.3 с, max 2.7 с. Ошибка стала тихой: 28 писем не ушли, клиент об этом не знает. Для урока это сильнее: зеленый ответ скрывает потерю |
| p99 2-3 с при 600 мс шлюза | 1.5-1.7 с при 600 мс | по указанию спеки задержка шлюза на ветке поднята до 900 мс (`MAILGW_DELAY_MS`, `compose/lesson-04.yml`) |
| фоновый `storm-short` | шторм ограничен 400 итерациями/с (`BG_STORM_RATE`) | замкнутый шторм даже на 200 VU разгоняется до ~3 100 RPS и упирает PostgreSQL в его 1 CPU (105 %): тогда акт 1 снова про базу. Прогон с полным штормом: pay p99 3.0 с, CPU базы 98-106 % (`full-storm-*.txt`) |

Попутная находка: запрос I5 в `invariant-checker` был коррелированным подзапросом по `payload->>'order_id'` и на
10 000 заказов упирался в `statement_timeout`. Переписан через агрегат и hash join.
