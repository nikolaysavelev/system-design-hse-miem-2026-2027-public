# Занятие 4. Результаты прогонов

Стенд: M4, Docker Desktop 8 ГБ, лимиты lesson-02 (soldout 2 CPU, PostgreSQL 1 CPU) + lesson-04. Сценарий `make checkout-storm`: checkout 150 VU × 90 с на мероприятии 2 и фоновый шторм 400 итераций/с на мероприятии 1. PSP 300 мс, почтовый шлюз 900 мс ± 30 %, 5 % ответов 502.

## Сценарий занятия целиком (26.09.2026 01:59-02:10, одна БД)

Так, как это увидят студенты: `make up` на `demo/l4-problem`, дальше `make switch` на otel и cdc без пересоздания базы. Сырые данные cdc: `act3/`.

| checkout-storm | problem | otel | cdc |
|---|---|---|---|
| pay p50 | 1 217 мс | 1 218 мс | **487 мс** |
| pay p95 | 1 630 мс | 1 571 мс | **605 мс** |
| pay p99 (порог 800 мс) | 2 301 мс ✗ | 2 301 мс ✗ | **703 мс ✓** |
| pay max | 2 608 мс | 2 619 мс | 807 мс |
| order p99 / tickets p99 | 105 / 2 мс | 95 / 3 мс | 182 / 177 мс |
| Ошибки HTTP | 0 % | 0 % | 0 % |
| Покупок за 90 с | 10 818 (118/с) | 10 828 (118/с) | **16 891 (187/с)** |
| CPU soldout (из 200 %) | 42-44 % | 23-51 % | 42-61 % |
| CPU PostgreSQL (из 100 %) | 45-59 % | 19-54 % | 102-109 % |
| Время БД, топ-10 запросов | 7.7 с | 8.6 с | 25.3 с |

Выводы:

1. На problem и otel pay ждет внешние системы: база работает 8 с из 90, CPU приложения меньше половины ядра, профиль показывает сетевые системные вызовы. Трейс (`act2/`) раскладывает 1.2 с pay на PSP 300 мс и шлюз 0.9-1.1 с, при 502 еще столько же на повтор.
2. Трейсинг с сэмплированием шумных маршрутов (hold, join, карта по 10 %, остальное 100 %) не изменил pay: p99 2 301 мс на обеих ветках. При 100 % на всех маршрутах хвост рос на 8 % (`act2/README.md`).
3. На cdc pay ждет только PSP: p99 703 мс, пропускная способность checkout выросла в 1.6 раза. Узкое место переехало в базу (CPU 102-109 %, order и tickets p99 около 180 мс): следующий шаг масштабирования про PostgreSQL, не про почту.
4. Доставка писем после cdc: задержка от commit оплаты до отправки p50 1.14 с, p99 2.65 с; лаг notifier 212-455 сообщений, в среднем 1.8 с.

## Что не совпало со спекой и что пришлось чинить

| Спека ожидала | Факт | Решение |
|---|---|---|
| акт 1: ошибки 2-5 % | 0 % | ошибка `Send` только логируется, таймаут хендлера 3 с почти не пробивается. Потеря стала тихой: 28 писем `failed` при 200 клиенту, а в длинных сценариях 27 и 43 заказа совсем без письма (таймаут отменял запись уведомления). Для акта 1 это сильнее исходного сюжета |
| p99 2-3 с при шлюзе 600 мс | 1.5-1.7 с | по указанию спеки `MAILGW_DELAY_MS=900` на стенде занятия |
| фоновый `storm-short` | фон 400 итераций/с (`BG_STORM_RATE`) | замкнутый шторм даже на 200 VU дает ~3 100 RPS и упирает PostgreSQL в 1 CPU: акт 1 снова стал бы про базу (`act1/full-storm-*`) |
| `booking/api.OrderPaid` | `OrderPaidEvent` | имя `OrderPaid` занято статусом заказа |
| миграции 0020, 0021 | плюс 0019 `orders(user_id, created_at)` | без индекса `GET /v1/users/{id}/tickets` сканирует `orders`; к третьей ветке это 5 мс на вызов и насыщение базы |
| | `autovacuum_naptime=5s` на стенде занятия 4 | на свежей БД план `count_user_holds` кэшировался при пустой `holds` и держался до первого autoanalyze: ~1 мс вместо 0.02 мс и 40+ с работы БД в первом прогоне. Воспроизводилось дважды, с настройкой ушло |
| 40 000 мест на мероприятие | 80 000 для `LESSON=04` | три checkout-storm за занятие продают ~45 000 мест мероприятия 2 |
| Tempo 0.5 CPU / 512 МБ | 1.5 ГБ, `GOMEMLIMIT`, restart | с 512 МБ Tempo убит OOM под штормом; после сэмплирования и трех прогонов держал 978 МБ |
| Tempo 3 `local-blocks` | в Tempo 3 процессор удален | TraceQL-метрики отдает live store без настройки |
| `make switch` | делегирует `switch-apply` Makefile'у целевой ветки | иначе при переходе otel → cdc не поднимался профиль cdc и не регистрировался коннектор |
| конфиг Prometheus по веткам | все цели с первой ветки | Prometheus не перечитывает смонтированный конфиг при switch: span-метрики и метрики notifier не собирались |
| лаг notifier как метрика notifier | отдельный экспортер `notifier-lag` | пока notifier стоит (`kill-notifier`), его метрики пропадают вместе с ним |
| semgrep: `paths` в правиле | область задает цель Makefile | semgrep в контейнере без `.git` молча отбрасывал все цели, проверка была пустой |

## Минимальный набор раздела E

Не понадобился: Debezium Connect 3.6 с PostgreSQL connector (pgoutput) и EventRouter завелся с первой регистрации коннектора (единственная правка: `table.op.invalid.behavior` принимает только `warn|error|fatal`). CDC работает на всех прогонах, `SELECT count(*) FROM outbox` = 0.
