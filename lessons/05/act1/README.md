# Акт 1. Реплики в compose

Ветка `demo/l5-k8s`, прогоны 02.10.2026. Сводка: `../results.md`.

## Монолит: `make scale SOLDOUT=2` под `make storm-short`

Оба прогона на одной базе, перед каждым `make holds-reset`. Файлы: `soldout-1/`, `soldout-2/` (`k6-summary.txt`, `docker-stats.txt`, `pgbouncer-pools.txt`, `pg-top.txt`, `invariants.txt`).

| | 1 реплика | 2 реплики |
|---|---|---|
| RPS | 2 643 | 2 590 |
| hold p99 | 886 мс | 898 мс |
| CPU PostgreSQL | 104-110 % | 104 % |
| CPU soldout | 66-73 % | 45 % + 45 % |
| PgBouncer `cl_active` / `cl_waiting` на 30-й и 50-й секунде | 24 / 16 и 37 / 3 | 20 / 60 и 45 / 35 |
| Инварианты | зеленые | зеленые |

Клиентских соединений стало 80 при тех же 20 серверных. Пропускная способность не изменилась: PostgreSQL занят на все свое ядро в обоих прогонах.

## Потребитель: `make scale NOTIFIER=3` и `make kill-notifier NOTIFIER_DOWN=75`

Свежая база на каждый прогон. Notifier остановлен на 20-й секунде checkout и запущен после конца нагрузки: время до нулевого лага это чистое время разбора очереди. Файлы: `notifier-1/`, `notifier-3/` (`kill-notifier.txt`, `lag-timeline.txt`, `consumer-group.txt`, `invariants.txt`).

| | 1 реплика | 3 реплики |
|---|---|---|
| Лаг на старте | 18 015 | 18 705 |
| До нулевого лага | 72 с | 32 с |
| Скорость разбора | ~250 сообщений/с | ~580 сообщений/с в среднем, до 1 780 после ребаланса |
| Участников группы и партиций | 1 участник, 3 партиции | 3 участника, по одной партиции |
| paid = notifications | 21 870 | 23 093 |
| Дублей | 0 | 0 |

Одна реплика ограничена своим параллелизмом: 256 писем одновременно при шлюзе в 0.9 с дают около 280 сообщений в секунду. Три реплики дают втрое больше слотов. Из 32 секунд 6-9 уходит на ребаланс группы, поэтому выигрыш 2.25 раза.

До исправления потребителя (см. `../results.md`) три реплики разбирали ту же очередь за 69 с: первая реплика забирала все три партиции и не отдавала их до конца очереди.
