Нагрузка в это время продолжалась: 3 реплики разобрали 5 600 сообщений очереди и входящий поток. pay p99 612 мс, ошибок 0; paid 74 259 = notifications 74 259, дублей 0.

Порог `lagThreshold: 200`: желаемое число реплик = лаг / 200. Под обычным checkout лаг держится 300-450, поэтому KEDA иногда держит 2 реплики и без слома.

HPA видит CPU подов 450m при request 500m и цели 70 % и добавляет реплики. RPS при этом падает на 11-12 %: PostgreSQL занят на все ядро, новые реплики добавляют клиентов в очередь PgBouncer. Сигнал CPU для монолита здесь ничего не говорит об узком месте.
