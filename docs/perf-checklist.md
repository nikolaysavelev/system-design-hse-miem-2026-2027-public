# Чек-лист производительности: что проверить до микросервисов

Порядок важен: каждый следующий пункт дешевле предыдущего только после того, как закрыт предыдущий. Пример применения — занятие 2 (`lessons/02/results.md`): baseline 55 % ошибок → шаг A (индексы, пул, PgBouncer) → шаг B (размер ответа, кэш) → шаг C (блокировки) → шаг D (вход).

## 0. Правило нуля

**Ошибки делают латентность красивой.** p99 при 55 % быстрых 5xx ничего не значит. Сначала `http_req_failed` → 0, потом хвосты. Оптимизация измеряется, а не обсуждается: гипотеза → профиль → исправление → повторная стрельба под теми же лимитами.

## 1. Измерь

- [ ] RED по маршрутам: `http_requests_total`, `http_request_duration_seconds` с явными бакетами до 5 с (дефолтные слепы на хвостах).
- [ ] Профиль CPU и alloc под нагрузкой (Pyroscope / `go tool pprof -top -seconds 20`). Пустой профиль без нагрузки бесполезен — стреляйте фоном.
- [ ] `pg_stat_statements` (сброс перед стрельбой): топ по `total_exec_time`, `mean_exec_time`, `rows`, `shared_blks_hit`.
- [ ] `pg_stat_activity`: `state`, `wait_event_type`, `wait_event`, количество — кто чего ждёт (Lock/advisory, LWLock, Client, IO).
- [ ] `docker stats` / cgroup: CPU и память каждого контейнера. Узкое место всегда одно — найдите, что упёрлось в 100 %.

## 2. Запросы

- [ ] `EXPLAIN (ANALYZE, BUFFERS)` для топ-5: Seq Scan на горячей таблице = индекс под фильтр; partial index под статусы (`WHERE status = 'active'`).
- [ ] Индекс — не бесплатно: каждый лишний индекс — запись на write path и `n_dead_tup`. Не добавляйте «на всякий случай»; HOT-update вылетает из partial-индекса.
- [ ] Нет `SELECT *`; нет N+1 (карта зала: один запрос статусов, не по запросу на место).
- [ ] Именованные запросы (`/* module.name */`) — иначе топ `pg_stat_statements` не связать с кодом.

## 3. Процесс под лимитами

- [ ] `GOMEMLIMIT` ≈ 85 % лимита контейнера, `GOGC` явно; `GOMAXPROCS` = CPU-квота (Go 1.25+ читает cgroup сам — проверьте в `/readyz`).
- [ ] Таймауты `http.Server`: `ReadHeaderTimeout`, `ReadTimeout`, `WriteTimeout`, `IdleTimeout`, `MaxHeaderBytes`; per-handler `context.WithTimeout` < `WriteTimeout`; контекст доходит до каждого I/O.
- [ ] Гистограммы с бакетами под ваши SLO; `go_memstats_*` и GC/с на дашборде.
- [ ] Фоновые батчи (expirer, reaper) — маленькими порциями с паузой, `FOR UPDATE SKIP LOCKED`, иначе всплеск p99 ровно в момент замера.

## 4. Соединения

- [ ] Пул приложения < `max_connections` (иначе «too many clients» — это ваш баг, не БД).
- [ ] Ожидание соединения ограничено (`503` + `Retry-After` вместо зависания); метрика `db_pool_acquire_wait_seconds`.
- [ ] Честно: пул не ускоряет — он переносит очередь из БД в приложение (закон Литтла). Помогает тем, что очередь дешевле и управляемее.
- [ ] Пулер (PgBouncer) нужен под N инстансов; цена: transaction pooling ломает сессионные фичи (сессионные advisory-lock, `SET`, `LISTEN`, temp-таблицы) и требует поддержки prepared statements (PgBouncer ≥ 1.21 + `max_prepared_statements`, либо `QueryExecModeExec`/simple protocol в pgx). `default_pool_size` меньше пула приложения — иначе пулер декорация.
- [ ] `statement_timeout`, `idle_in_transaction_session_timeout` на сервере — длинные транзакции не должны жить вечно.

## 5. Размер ответов

- [ ] Что клиенту нужно на самом деле? Карта зала целиком (800 КБ × 200 RPS = 1.3 Гбит/с) → сводка по секторам + сектор по запросу (32 КБ) + дельты (SSE).
- [ ] `ETag` от версии из БД, `If-None-Match` → 304; предсобранные представления (`[]byte`), не сериализация на каждый запрос.

## 6. Кэш

- [ ] Кэшируются **только проекции** (отображение), никогда — истина, от которой зависят инварианты. Кэш не читается в пути записи (hold, pay).
- [ ] Версия — из БД (счётчик в той же транзакции, что и проекция); запись в кэш только если `version_new >= version_cached` (CAS), инвалидация **после** commit.
- [ ] TTL как страховка от потерянного события, а не как механизм консистентности; `singleflight` на промах.
- [ ] Умейте сломать: выключите инвалидацию и покажите, что инварианты целы, а карта врёт.

## 7. Блокировки

- [ ] Уникальный индекс вместо блокировки: `INSERT … ON CONFLICT DO NOTHING RETURNING` — конфликт мгновенный, очереди нет. Блокировка, дублирующая индекс, только создаёт очередь.
- [ ] «Любой из N» — `FOR UPDATE SKIP LOCKED` / случайный старт по кандидатам; гонку всё равно закрывает индекс.
- [ ] Короткие транзакции: внешние вызовы (PSP) — вне транзакции; идемпотентность — в той же транзакции, что и эффект.
- [ ] Сессионные advisory lock под пулером запрещены; транзакционные — допустимы, но подумайте, нужны ли.

## 8. Регулирование входа

- [ ] Очередь допуска (waiting room) с admission rate: превращает отказ в ожидание — это продуктовое решение, и ручку крутите вы.
- [ ] Rate limit на периметре (по токену/пользователю), не только по IP.
- [ ] Ожидание — дёшево (Valkey, SSE/long-polling), покупка — дорого (PostgreSQL): держите их на разных путях.

## 9. Только после этого — выделение сервиса

Критерии: отдельный профиль нагрузки, отдельный темп изменений, отдельная команда. Если после пунктов 1–8 узел всё ещё не справляется — занятие 3.
