# ADR-002. Где живёт состояние очереди допуска (waiting room)

- **Status:** Accepted (занятие 2, 12.09.2026)
- **Date:** 2026-09-12
- **Deciders:** преподаватель, обсуждение с группой (CBAM-lite)

## Context

Расчёт нагрузки (`spec/soldout.md`, раздел 5): 400 000 RPS наивного опроса «где моя очередь» против 1 500 TPS консистентной части. Очередь допуска должна (а) выдерживать порядок 10⁵ RPS на статус, (б) выдавать допуски с управляемой скоростью (`ADMISSION_RATE`), (в) не терять пользователей при рестарте приложения, (г) не превращать PostgreSQL в узкое место раньше, чем это сделает бронирование. Стенд: один инстанс приложения; на занятии 5 их станет N. Занятие 2 показало (`lessons/02/results.md`), что после шагов A–C узкое место — CPU PostgreSQL на самом бронировании; статус очереди в PostgreSQL добавил бы к нему опрос.

## Options

| | A. Только Valkey | B. Только PostgreSQL | C. Valkey как порядок и rate limit + PostgreSQL для допусков + AOF `everysec` |
|---|---|---|---|
| Что это | sorted set `queue:{event}`, token bucket, допуски — тоже ключи | таблица `queue_positions` + `admissions`, `SELECT … FOR UPDATE SKIP LOCKED` для admitter | позиция и inflight — Valkey (Lua-атомарность), выданные допуски — `admissions` в PG; Valkey с AOF `appendfsync everysec` |
| Cost: разработка | 2 | 2 | 3 |
| Cost: эксплуатация | 2 (+ Valkey как stateful) | 1 | 3 (два хранилища, две модели отказа) |
| Cost: риск | 4 (потеря очереди и допусков при падении Valkey без персистентности) | 3 (PG — единая точка, опрос бьёт по OLTP) | 2 (потеря ≤ 1 с позиций; допуски переживают рестарт) |
| Benefit: латентность статуса (p99 < 5 мс при 10⁵ RPS) | 5 | 1 | 5 |
| Benefit: консистентность допусков (не выдать дважды, не потерять выданный) | 2 | 5 | 4 |
| Benefit: изоляция OLTP от опроса | 5 | 1 | 5 |
| **ΣBenefit − ΣCost (оценка автора)** | +4 | +1 | **+6** |

## Decision

Вариант **C**. Очередь (`ZADD queue:{event}`) и admitter (token bucket + `ZPOPMIN` + `inflight` в одном Lua-скрипте) — в Valkey: это данные с коротким временем жизни и жёстким требованием к латентности. Выданные допуски дублируются в PostgreSQL `admissions` (так уже с занятия 1): допуск — обещание пользователю, его нельзя терять. Valkey включает AOF `everysec`: при падении теряется не более секунды позиций, что для waiting room приемлемо и честно описано в `spec/soldout.md`. `QUEUE_ENABLED=false` возвращает поведение занятия 1 (допуск сразу).

Последствия для стенда: `/readyz` с obs-профилем занимает ≤ 90 с на чистой машине (осознанное отклонение от NFR-10 «≤ 60 с» — из-за Pyroscope/Alloy/exporters; без obs — как раньше).

## Consequences

Плюсы: опрос статуса не касается PostgreSQL; rate — ручка `ADMISSION_RATE`, которую видно на панели `soldout-queue`; выданные допуски восстанавливаются из PG. Минусы: два хранилища с разной моделью отказа; при равных `ts` в sorted set порядок лексикографический по `user_id` (сказать честно); один admitter на процесс — при N инстансах rate глобальный только с лидером или разделённым бюджетом.

## Сильнейший аргумент против

«B, потому что один Valkey — лишний stateful-компонент, а 10⁵ RPS у нас не будет».

## Revisit when

- N инстансов приложения (занятие 6): admitter нужен один — лидер (Valkey lock / k8s lease) или раздельные бюджеты по инстансам;
- потеря Valkey должна стать безопасной (занятие 14): снапшоты очереди в PG или пересборка очереди из `admissions`;
- FIFO-справедливость между репликами / регионами.
