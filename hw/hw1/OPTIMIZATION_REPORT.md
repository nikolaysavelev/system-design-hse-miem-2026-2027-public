# Отчет об оптимизации (шаблон для этапов 3–4 HW1)

Заполняется в `hw/hw1/SOLUTION.md` (раздел "Измерения") или как отдельный файл. Обязательное правило: **сначала ошибки → 0, потом хвосты**; p99 при ненулевых 5xx не интерпретируется.

## 1. Условия

| Параметр | Значение |
|---|---|
| Стенд | лимиты стенда занятия 5 (PostgreSQL 1 CPU / 1 ГБ, soldout 2 CPU / 512 МБ); режим full или lite |
| Сценарии | ваш сценарий `k6/<variant>.js` (обязательно); `make storm` для контроля, что путь `hold` не деградировал |
| Ветка / коммит | |
| Дата, ноутбук | |

## 2. Таблица до/после (обязательна)

| Шаг | RPS | Ошибки (5xx) | p50 / p95 / p99 главного шага вашего сценария, мс | p99 hold в `make storm`, мс | Время БД, топ-5 `pg_stat_statements`, с | `make invariants` |
|---|---|---|---|---|---|---|
| Baseline | | | | | | |
| Исправление 1: `<что>` | | | | | | |

Источники: `make results` (из `k6/results/*.json`), `make pg-top` (сброс перед стрельбой: делается автоматически), `docker stats`.

## 3. Гипотеза → доказательство → исправление → повторный замер

Для каждого исправления:

1. **Симптом** (какая метрика красная, где на дашборде).
2. **Гипотеза** и чем проверена: flame graph (`make pprof-top` или Pyroscope), трейс (`make traces-slow`), `EXPLAIN (ANALYZE, BUFFERS)`, `pg_stat_activity` (`wait_event`), `pg_stat_statements`.
3. **Исправление** (коммит, миграция, конфиг): одно на шаг.
4. **Повторный замер** под теми же лимитами и цифра эффекта (в %, по той же метрике).

## 4. Что не стал оптимизировать и почему (обязательно)

Минимум один кандидат с аргументом: эффект мал по профилю / цена на write path / ломает инвариант / это следующее занятие (outbox, очередь).

## 5. Как использовался ИИ

Инструмент; что предложил агент по `pg_stat_statements`/профилю; что из этого приняли, что отвергли и почему (особенно предложения кэшировать истину или убрать проверку лимита).
